## 작성 규칙

### 파일명 규약
- 파일명 형식: **`000N-<title-slug>.md`** — 4자리 0-padded 일련번호 + kebab-case 제목 슬러그
  - 예: `0001-ssot-deviations.md`, `0002-rag-vendor-decision.md`
- 일련번호는 **결정 시점 순서**로 부여하며 결번을 두지 않는다(중간에 폐기되어도 번호는 보존하고 상태만 `Superseded`로 변경).

### 필수 섹션 구조

#### 단일 결정 ADR (기본 패턴)
하나의 결정만 다루는 ADR은 다음 6개 H2 섹션을 **고정 순서**로 포함한다.

1. `## 상태` — `Accepted | Proposed | Superseded | Deprecated` 중 하나
2. `## 맥락` — 결정이 필요했던 배경, 제약 조건
3. `## 결정` — 채택한 방향
4. `## 근거` — 채택 이유(대안 비교 포함)
5. `## 영향받는 산출물` — 관련 PRD FR 번호, Epic/Story 번호, 코드 파일 경로(상대 링크)
6. `## 날짜·승인자` — `YYYY-MM-DD · 승인자 이름(역할)` 형식

#### 다중 결정 ADR (예외 패턴)
동일 시점·동일 맥락(예: 단일 미팅에서 일괄 확정된 SSOT 편차 묶음)에서 **여러 결정을 함께 등재**하는 경우, 결정 단위로 H2 섹션을 두고 그 안에 위 6개 섹션을 **H3로** 포함한다. 예시 구조:

```markdown
## 결정 #1 — <제목>
### 상태
### 맥락
### 결정
### 근거
### 영향받는 산출물
### 날짜·승인자

## 결정 #2 — <제목>
### 상태
...
```

단, 단일 ADR에 묶을 수 있는 결정은 **3~5건 이내**가 권장 한도이며, 각 결정이 같은 맥락·같은 승인자·같은 시점을 공유해야 한다. 그렇지 않으면 단일 결정 ADR 여러 개로 분리한다. 본 디렉터리 `0001-ssot-deviations.md`가 이 패턴의 사례다.

### 메타 블록(YAML 또는 마크다운 인용 블록)
파일 상단(H1 바로 다음 줄)에 5종 필드 메타 블록을 포함한다.

```markdown
> **최종 수정일:** YYYY-MM-DD
> **작성자:** {이름}
> **승인자:** (인수자 검토 시 기입)
> **버전:** v1.0
> **관련 FR/Story:** FR{XX}·FR{XX} / Story {X.Y}·{X.Y}
```

**`관련 FR/Story` 필드 작성 규약:**
- FR 번호와 Story 번호는 **슬래시(` / `)로 구분**
- 같은 종류 내부는 **가운뎃점(`·`)으로 구분**
- ADR 본문 §영향받는 산출물에 등장하는 모든 FR·Story 번호를 메타에 빠짐없이 나열 (그루핑·요약 금지)
- 인덱스 표(README.md ADR 인덱스)도 동일 형식 유지

### 상태 라이프사이클
- `Proposed` → 제안 단계, 검토 진행 중
- `Accepted` → 채택, 시행 중
- `Superseded by NNNN` → 새 ADR로 대체됨(본 ADR은 보존, 본문 상단에 후속 ADR 링크)
- `Deprecated` → 더 이상 유효하지 않으나 역사적 기록으로 보존

### 변경 관리
- ADR 본문 수정은 **오타·링크 갱신** 외에는 원칙적으로 금지. 결정 자체가 바뀌면 새 ADR을 생성하고 기존 ADR을 `Superseded`로 표시한다.
- 본 인덱스(`README.md`)는 신규 ADR 추가 시마다 표 행을 1줄 추가한다.
